# 결함 재현과 원인 분석

> [주제 목차](/docs/tutorial/테스트와-디버깅/) · 이전: [진단 도구와 계층](/docs/tutorial/테스트와-디버깅/진단-도구와-계층) · 다음: [회귀 확인 습관](/docs/tutorial/테스트와-디버깅/회귀-확인-습관)

이 문서의 결과: GlobalID로 실패한 거래 하나를 끝까지 추적해 원인을 찾는다.

## GlobalID를 확보하는 것이 첫 걸음

GlobalID는 요청 한 건을 끝까지 추적하는 열쇠입니다. 오류 보고를 받으면 가장 먼저 해당 요청의 GlobalID를 확보하는 습관을 들입니다. 사용자에게 "몇 시쯤, 어느 화면에서" 정도만 들어도 거래 이력에서 근접한 GlobalID를 찾을 수 있습니다.

## 자주 만나는 증상과 우선 확인 지점

| 증상 | 우선 확인 |
|---|---|
| 화면에 아무 반응이 없음 | 네트워크 탭에서 요청 자체가 나갔는지 |
| 200 응답인데 화면이 비어 있음 | 데이터 맵 이름(`syn-datafield`/`outputs`/`Outputs`) 일치 여부 |
| 거래 이력에 오류 코드가 남음 | 계약 파일 문법(JSON/XML), 파라미터 이름 오타 |
| 특정 사용자만 실패 | `Authorize` 설정과 인증 토큰 상태 |

이 표의 두 번째 증상은 [08. transact 거래 계약](/docs/tutorial/transact-거래계약/CRUD-거래-연결과-검증)에서 직접 재현해 본 상황과 같습니다. 실습에서 겪은 문제를 실제 장애에서도 같은 방식으로 알아볼 수 있어야 합니다.

## 실습: 계약 오류 재현하기

1. `BOD010.xml`의 SQL 파라미터 이름(`@Category`)을 일부러 오타(`@Categry`)로 바꿉니다.
2. `BOD010` 화면에서 조회를 실행합니다.
3. 거래 이력 또는 응답 본문에 나타나는 오류 메시지를 확인합니다.
4. 오타를 원래대로 되돌리고 다시 조회해 정상 동작을 확인합니다.

이 과정을 한 번 경험해 두면 실제 운영에서 비슷한 오류 메시지를 만났을 때 "계약 파일의 파라미터 이름을 먼저 의심"하는 판단을 빠르게 할 수 있습니다.

## 성공 증거

- [ ] 실제 GlobalID 하나를 골라 화면 요청부터 서버 로그까지 추적했습니다.
- [ ] 의도적으로 만든 오류의 메시지와 실제 원인을 짝지었습니다.
