# SQL·거래·화면의 결과 비교하기

화면이 비어 있을 때 원인을 한꺼번에 추측하지 말고 SQL → 거래 → 화면 순으로 확인합니다. 개발 서버와 실습 데이터 원본을 먼저 준비하세요.

:::warning ‘조회’도 실행 전에 SQL을 확인하세요

현재 새 프로젝트 템플릿의 `LD01`에는 `CREATE TABLE`과 초기 데이터 `INSERT`가 포함되어 있습니다. 조회 버튼도 DB를 변경할 수 있습니다. 실제 `.dbc`를 읽고 **별도의 실습 DB**인지 확인한 뒤 실행하세요. README의 DDL과 계약 SQL이 다르면 먼저 스키마·키 타입을 대조합니다.

:::

## 1. SQL 계약부터 확인

1. **개발 > dbclient**에서 `LAB010.dbc`를 엽니다.
2. 왼쪽 계약 구성에서 `LD01`을 선택합니다.
3. 헤더의 데이터 원본과 SQL, 파라미터를 확인한 뒤 저장합니다.
4. **쿼리 실행**으로 결과와 메시지를 확인합니다.

현재 생성 예제의 검색 입력은 `SearchItemName`, `SearchUseYN`입니다. 설치 버전의 파일에 있는 이름과 기본값을 기준으로 사용하세요. `.dbc`의 파라미터에는 `@`가 붙지만 거래 입력 필드는 해당 이름을 기준으로 비교합니다.

## 2. 거래 계약 실행

1. **개발 > transact**에서 `LAB010.txn`을 열고 `LD01` 서비스를 선택합니다.
2. 저장한 뒤 **거래 실행**을 엽니다. 서비스 선택 전에는 실행 버튼이 비활성화됩니다.
3. **입력값**에 SQL 시험과 같은 조건을 넣고 **요청 JSON**에서 식별자·데이터 맵을 확인합니다.
4. 실행 후 응답의 **Table**과 **JSON**을 비교합니다. HTTP 200이어도 거래 오류가 있을 수 있습니다.

입력칸이 비어 있고 모델 ID가 `Dynamic`이면 필드를 직접 추가해 `SearchItemName`, `SearchUseYN`을 넣습니다. SQL 시험에 사용한 값과 동일하게 맞추세요.

개발 서버는 저장된 계약을 읽습니다. 미저장 경고를 무시하면 이전 내용으로 실행될 수 있습니다. 실행 팝업을 닫으면 진행 중인 요청이 취소되지만, 이를 이미 반영된 DB 변경의 복구로 해석해서는 안 됩니다.

## 3. 화면에서 같은 조건 실행

브라우저의 `LAB010`에서 같은 검색 조건으로 조회합니다. 결과가 다르면 오른쪽 **연관 계약 찾기**로 화면 → transact → dbclient를 따라가세요. 이 도구는 저장된 파일을 기준으로 하므로 수정 후 저장·새로 고침이 필요합니다.

| 시험 | 확인할 결과 |
|---|---|
| 검색값 비움 | SQL·거래·화면의 행 수와 키가 일치 |
| 존재하는 항목명 일부 | 조건에 맞는 행만 표시 |
| 존재하지 않는 항목명 | 빈 결과이며 실행 실패와 구별됨 |

## 직접 확인

각 시험의 입력값, 결과 건수, 오류 유무를 한 줄씩 기록하세요. SQL만 성공하면 [계약·매핑 진단](../reference/문제-해결.mdx#거래와-화면-결과)을 확인합니다. 거래 문법 전체는 [거래 호출 참조](/docs/reference/거래-호출)에서 찾습니다.
