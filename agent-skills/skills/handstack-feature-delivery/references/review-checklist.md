# 구현 검토 체크리스트

변경을 보고하기 전에 자기 검토한다. 항목마다 "확인함 / 해당 없음 / 확인 못 함(이유)"을 구분한다.

## 연결 일치
- [ ] 화면 `transaction` 키 = `.txn` `ServiceID` = 실행 계약의 id (대소문자 포함)
- [ ] 입력 `dataFieldID`·출력 `dataFieldID`가 HTML의 `<form syn-datafield>`/컨트롤/`syn_data`와 일치
- [ ] 전송 컨트롤마다 `belongID`에 이 거래 ID 포함, 그리드 열 8번째 값 확인
- [ ] 출력 개수·순서 = SQL 결과 집합(필요 시 `.txn` Outputs, `DisposeResult` 제외 개수)
- [ ] 다중 `seq`가 입력 순서와 일치, `(id, seq)` 중복 없음
- [ ] `syn-events`에 선언한 이벤트마다 핸들러, 새 핸들러마다 선언 (`hs_inspect.py --verbose`)

## 데이터·SQL
- [ ] 모든 `@Param` 선언 + 타입/길이가 컬럼과 맞음, 사용하지 않는 파라미터 제거
- [ ] 값은 바인딩. 식별자(테이블·컬럼·정렬)는 고정 분기 또는 `<filters>` 허용 목록
- [ ] `value="NULL"`이 빈 문자열이라는 점을 고려한 숫자/날짜 처리
- [ ] 저장/삭제 서비스 `TransactionScope true`, 부모-자식 순서와 키 전달
- [ ] 업무 오류는 `Exception` 집합(첫 출력), 오류 메시지에 민감정보 없음
- [ ] 대량 조회에 조건·페이징, N+1 방지(조인/집합 반환)

## 규칙·동시성
- [ ] 업무 규칙이 한 줄에 판단 하나로 정리되고 강제 위치(화면/SQL/함수/DB 제약)가 정해졌다 — 복잡하면 `handstack-rules-and-verification`
- [ ] 화면 검증과 별개로 서버가 저장 직전 규칙을 다시 검사한다
- [ ] 한도·중복·상태 전이: 경계값(한도-1, 한도, 한도+1)과 기준 시각 경계를 테스트했다
- [ ] 같은 대상·같은 사용자의 동시 저장, 응답 유실 뒤 재시도에서 중복 저장되지 않는다(`TransactionScope`, 잠금 순서, 유일 제약)
- [ ] 업무 오류를 `Exception` 결과로 돌려준 뒤 같은 요청의 다른 seq가 변경을 계속하지 않는다(롤백은 예외에서만)

## 보안·권한
- [ ] `Authorize`/`Roles`/`AccessScreenID`가 의도한 호출 화면만 허용, 공개 거래 범위를 넓히지 않음
- [ ] 사용자/회사 식별자 같은 권한 범위 값은 서버가 주입하는 토큰 변수(`@$이름` 파라미터)를 쓰고 화면 hidden 값만 믿지 않음
- [ ] 키·토큰·연결 문자열·실제 URL을 소스·로그·출력에 새로 쓰지 않음
- [ ] 파일 업로드: 크기/확장자 정책과 경로 안전성, 다운로드 접근 범위

## 화면 품질
- [ ] 조회/저장/삭제 후 상태: 빈 결과, 입력 오류, 업무 거절, 통신 오류, 결과 불명이 각각 사용자에게 구분되어 표시(`handstack-screen-development`의 `references/ux-states.md`)
- [ ] 삭제·되돌릴 수 없는 작업에 확인 대화상자
- [ ] 저장 성공 판정이 `Exception.Error` 등 서버 계약 값 기준(`$string.toBoolean`)
- [ ] 선택 행/포커스 복원, 크기 조정(`pageResizing`)
- [ ] 프로젝트 `DESIGN.md` 준수(팝업 방식, 컨테이너, 색·아이콘, 라벨 배치)와 접근성(`aria-label`)
- [ ] 기존 파일의 인코딩·줄바꿈·들여쓰기 유지, 신규 주석 정책 준수
