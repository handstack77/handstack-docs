## 1. 검증과 확인

검증(verification)은 명세대로 만들었는가, 확인(validation)은 사용자의 실제 목적에 맞는가이다. 규칙 표와 결정표는 검증의 기준이고, 인수 조건(사용자가 업무를 끝까지 수행)은 확인의 기준이다. 일부 케이스 통과는 결함이 없다는 증명이 아니다.

## 2. 수준과 유형

| 수준 | HandStack에서의 대상 |
|---|---|
| 정적 | 계약·화면 연결 점검(`hs_inspect.py`), SQL 리뷰, 규칙 표 검토 |
| 단위/구성요소 | 순수 계산·판단 함수, 단일 `.dbc` statement (테스트 DB) |
| 통합 | 거래 한 건 실행(`.txn` → 실행 계약), 여러 seq의 트랜잭션, 함수와 DB |
| 시스템 | 화면 시나리오(진입 → 조회 → 저장 → 확인), 권한별 시나리오 |
| 시스템 통합 | 외부 시스템 연계(command/graph/repository) |
| 인수 | 실제 업무 사용자의 시범 수행 |

기능·성능·보안·접근성은 수준과 다른 **유형** 축이다. 단위 테스트도 보안을 확인할 수 있고 시스템 테스트도 성능을 볼 수 있다.

## 3. 기법

- 동등 분할: 같은 방식으로 처리되는 입력 집합에서 대표값.
- 경계값: 허용/거절이 갈리는 지점(한도-1, 한도, 한도+1; 날짜의 마지막 순간과 다음 순간; 빈 문자열/공백/최대 길이).
- 결정표: 조건 조합 — [결정표](decision-tables.md).
- 상태 전이: 허용된 상태 변화와 금지된 변화(이미 취소된 건의 재취소).
- 구조 기반: 분기 실행 범위. 커버리지 숫자가 요구 충족을 뜻하지는 않는다.

## 4. 규칙 → 테스트 표

| ID | 규칙 | 사전 상태 | 입력/조작 | 기대 결과(응답 + 최종 데이터) | 수행 수준 |
|---|---|---|---|---|---|

기대 결과에는 응답 메시지만 쓰지 말고 **저장 데이터 변화 없음/건수/이력 보존**을 적는다. 필수 케이스: 정상, 각 거절 사유, 경계 3점, 대상 없음, 잘못된 입력, 권한 없는 계정(거절되고 변경 없음), 이미 처리된 건 재요청, 동시 요청, 응답 유실 후 재시도.

## 5. 결정론적 테스트 (시간·데이터)

- 기준 시각을 **인자나 설정으로 주입**할 수 있게 한다. SQL이 현재 시각 함수를 직접 쓰면 경계 테스트가 어렵다 — 서버 시각을 쓰기로 한 규칙이면 테스트 데이터의 날짜를 상대적으로 만들되 자정 경계 실행을 피한다.
- 테스트 데이터는 만든 것만 정리한다. 공용·운영 데이터를 지우거나 갱신하지 않는다.
- 날짜 규칙은 시간대를 명시한다(서버 기준 날짜인지 사용자 기준인지).

## 6. 수행 수준 보고

각 케이스를 `정적 / SQL 단독 / 거래 실행 / 화면 / 미수행`으로 표시한다. 미수행에는 이유(환경 없음, 승인 없음)를 적고 위험을 한 줄로 쓴다. "통과"는 실행한 것에만 쓴다.

## 7. 결함 기록

| 항목 | 내용 |
|---|---|
| 환경/버전 | 모듈 버전, 환경(개발/검증), 브라우저 |
| 사전 상태 | 데이터·권한·설정 |
| 재현 절차 | 화면 ID, 조작 순서, 입력값(비식별) |
| 기대 / 실제 | 응답 + 최종 데이터 |
| 증거 | 시각, `GlobalID`, 콘솔/서버 로그 일부(토큰·키 제거) |
| 심각도 / 우선순위 | 심각도=영향(데이터 손상은 사용자 수가 적어도 높음), 우선순위=처리 순서 |

수정 뒤에는 재현 케이스가 해결됐는지, 인접 기능이 깨지지 않았는지(회귀)를 확인하고 원인 계층(`handstack-troubleshooting`)을 함께 적는다.

## 8. 출시 판단

"전부 통과"만으로 판단하지 않는다. 다룬 요구와 위험, 중대한 미해결 결함, 데이터 이전·복구 절차, 권한 설정, 운영 안내, 모니터링할 지표(성공률, 거절 사유별 건수, 저장 오류, 응답 시간)를 점검한다. 백업은 복원 연습까지 해야 유효하고, 되돌릴 수 없는 DB 변경이 있으면 코드 롤백만으로 복구되지 않는다.
