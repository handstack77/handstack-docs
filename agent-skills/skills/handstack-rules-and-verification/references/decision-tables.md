# 결정표와 테스트 도출

## 목차
1. 언제 쓰는가
2. 작성 절차
3. 예(일반 승인 규칙)
4. 완전성·배타성 검증
5. 구현으로 옮기기
6. 흔한 실수

## 1. 언제 쓰는가

판단 조건이 셋 이상이거나, 여러 조건이 겹칠 때 표시할 **사유의 우선순위**가 필요할 때, 규칙 변경이 잦을 때. 단순 필수 입력 검사는 필요 없다.

## 2. 작성 절차

1. 입력 조건을 불리언(Y/N)으로 정의한다. 이름 앞에 의미를 둔다(예: 활성 여부, 한도 여유, 승인 가능 상태).
2. 먼저 **검증 단계**(형식, 권한, 대상 존재)를 분리한다. 이것이 실패하면 결정표에 들어가지 않고 별도 오류다. "조회 실패/알 수 없음"을 N으로 바꾸지 않는다.
3. 우선순위를 정한다(비활성 → 연체 → 한도 → 상태 …). 위쪽 조건을 충족한 경우에만 다음 사유에 도달하게 열을 구성하면 한 입력이 한 규칙에만 일치한다.
4. 열(규칙)별 결과를 적는다. 값이 결과에 영향을 주지 않을 때만 `—`로 압축한다.
5. 열마다 테스트 한 건을 만들고(아래 4절), 경계값은 별도로 추가한다.

## 3. 예(일반 승인 규칙)

| 조건·행동 | R1 | R2 | R3 | R4 | R5 |
|---|---|---|---|---|---|
| A: 대상 사용자가 활성 | N | Y | Y | Y | Y |
| O: 처리 지연 건 존재 | — | Y | N | N | N |
| L: 진행 건수 < 한도 | — | — | N | Y | Y |
| C: 대상 자원이 사용 가능 | — | — | — | N | Y |
| 결과 | 비활성 거절 | 지연 거절 | 한도 거절 | 자원 거절 | 등록 시도 |

조건 4개의 전체 조합은 16개다. R1은 A=N인 8개, R2는 4개, R3은 2개, R4와 R5는 각 1개로 합계 16이고, 열 사이에 겹침이 없다.

## 4. 완전성·배타성 검증

- 완전성: 규칙이 덮는 조합 수의 합 = 2^조건 수. 합이 맞아도 겹침이 있으면 다른 조합이 빠진다.
- 배타성: 아무 입력 하나를 골라 두 개 이상의 열에 일치하는지 확인한다.
- 실제 데이터에는 논리적으로 불가능한 조합이 있을 수 있다(예: 지연 건이 있는데 진행 건수 0). 이 조합은 순수 함수 테스트에서는 넣되, DB 통합 테스트에서는 데이터로 만들 수 없음을 표시한다.
- 사유를 여러 개 한꺼번에 반환하는 정책으로 바꾸면 "결과는 하나"라는 가정부터 다시 설계한다.

## 5. 구현으로 옮기기

- SQL: 우선순위 순서의 `CASE` 또는 조건별 사전 조회 → `<if test>` 분기 → 맨 앞 `Exception` 결과로 사유 반환. 사유 코드는 규칙 ID와 같은 값을 쓰면 추적이 쉽다.
- 표의 조건 계산(활성, 지연, 건수)은 한 곳(한 `.dbc` 또는 한 함수)에서 구하고, 화면에는 결과 사유만 전달한다.
- 규칙이 바뀌면 표를 먼저 고치고 테스트를 갱신한 뒤 구현을 바꾼다. 기존 데이터에 소급 적용할지는 별도 결정이다.

## 6. 흔한 실수

- 우선순위 없이 여러 분기를 나열해 입력에 따라 사유가 달라짐
- 경계 `<` 와 `<=` 혼동 — 표의 조건 문장에 "미만/이하"를 명시
- 조회 서비스와 저장 서비스가 같은 규칙을 다르게 구현
- 테스트 데이터가 현재 날짜에 의존해 실행일에 따라 결과가 바뀜 → 기준 시각을 인자로 주입
