## 1. 먼저 던질 질문

데이터를 바꾸는 서비스마다 답을 적는다.

1. 같은 대상에 두 사용자가 동시에 저장하면 몇 건이 성공해야 하는가?
2. 같은 사용자가 서로 다른 대상 두 개를 동시에 저장하면 집계 한도가 지켜지는가?
3. 저장은 됐는데 응답이 유실돼 사용자가 다시 누르면 중복 저장되는가?
4. 부모-자식 여러 statement 중 중간이 실패하면 어디까지 남는가?
5. 화면을 거치지 않는 경로(관리 SQL, 배치, 다른 서비스)가 같은 규칙을 우회하는가?

## 2. HandStack에서 확인된 동작 (dbclient 소스 기준)

아래는 소스를 읽어 확인한 내용이며 실행 환경에서 다시 확인하기 전에는 보장으로 쓰지 않는다.

- `.txn` 서비스의 `TransactionScope: true`이면 요청의 모든 statement가 **하나의 연결·트랜잭션**에서 실행되고, 끝까지 예외 없이 가면 한 번에 커밋된다. `false`이면 statement별로 자동 커밋이라 중간 실패 시 앞선 변경이 남는다.
- 격리 수준 우선순위: statement 파일 header의 `<isolation>` → 데이터 원본(`DataSource`)의 `TransactionIsolationLevel` → `ReadCommitted`. 값은 .NET `IsolationLevel` 이름이어야 하며(`ReadCommitted`, `RepeatableRead`, `Serializable`, `Snapshot` 등) **이름이 틀리면 트랜잭션을 시작하지 않는 것으로 읽힌다** — 오타를 내지 말고 실행으로 확인한다. DBMS가 지원하지 않는 수준은 오류가 날 수 있다.
- **롤백은 예외나 명령(before/after command) 오류일 때만** 일어난다. SQL의 `TRY/CATCH`로 오류를 잡아 `Exception` 결과(첫 결과 집합)로 돌려주는 관례는 정상 응답이므로 **커밋된다**. 따라서 같은 요청의 다른 seq가 이미 쓴 변경은 남는다.
  - 업무 오류를 결과로 돌려주려면 **오류를 판정한 뒤에는 변경 SQL을 실행하지 않도록** 같은 batch 안에서 검사 → 쓰기 순서를 지키고, 이후 seq의 SQL도 같은 조건을 다시 검사하게 한다(statement는 서로의 오류 결과를 보고 자동으로 건너뛰지 않는다).
  - 요청 전체를 되돌려야 하면 SQL에서 예외를 다시 던져(`THROW` 등) 요청 실패로 만든다. 이때는 `Exception` 결과 관례 대신 `exceptionText` 오류가 화면에 전달된다는 점을 화면과 합의한다.
- 서버의 `IsValidationGlobalID`가 켜져 있으면 `GlobalID`는 1회용이다(재전송 방지). **업무 멱등성이 아니다**: 사용자가 응답을 못 받고 다시 누르면 새 `GlobalID`로 새 요청이 들어온다.
- 다른 서비스·함수·외부 호출을 섞은 순차 거래(`S`)와 워크플로(`W`)는 전체 롤백이 자동 보장되지 않는다.

## 3. 집계 한도·중복 방지 패턴

행 단위 CHECK로는 "회원당 N건"처럼 다른 행을 센 값을 강제할 수 없다. 쓰기 경로를 **하나로 모은다**.

1. 하나의 `TransactionScope: true` 서비스에서 시작한다(필요하면 `<isolation>` 지정).
2. 경합하는 상위 행(회원, 계정, 재고 같은 "누구 몫인가"의 행)을 먼저 잠그고, 이어서 대상 행을 잠근다. **모든 쓰기 경로가 같은 순서**를 쓴다(교착 방지).
3. 잠금을 얻은 뒤 상태를 **다시 조회**해 규칙을 검사한다(잠금 전에 읽은 값을 믿지 않는다).
4. 허용되면 같은 기준 시각으로 값을 정해 삽입/갱신한다.
5. 같은 대상의 중복 점유처럼 행 단위로 표현되는 불변 조건은 DB 유일 제약/조건부 유일 인덱스로 한 번 더 막는다. 위반 오류는 업무 메시지로 변환한다.

잠금 문법은 DBMS마다 다르다(`SELECT … FOR UPDATE`, SQL Server의 잠금 힌트 등). SQLite는 행 잠금이 없고 쓰기 시 데이터베이스 단위로 직렬화된다. 사용하는 DBMS의 문서로 확인하고, 방언 차이를 `.dbc` 헤더의 `<use>`/데이터 원본 단위로 분리한다. 직접 SQL을 쓰는 다른 경로가 있으면 이 보장이 깨진다 — 쓰기 권한을 제한하거나 검증을 공통 함수/프로시저에 모은다.

## 4. 재시도와 응답 유실

- 화면: 요청 중 저장 버튼을 비활성화하고 입력값을 보존한다. 오류 응답과 **응답 없음**(결과 불명)을 구분해, 후자는 "저장 여부 확인 중"으로 보여 주고 조회로 결과를 확인하게 한다(`handstack-screen-development`의 `references/ux-states.md`).
- 서버: 같은 업무 요청이 반복돼도 중복 생성되지 않게 **업무 키**를 설계한다 — 클라이언트가 만든 요청 키를 저장 컬럼에 두고 유일 제약을 건다. 같은 키로 같은 내용이면 기존 결과를 돌려주고, 같은 키로 다른 내용이면 충돌로 처리한다. 키가 있다는 사실만으로 멱등성이 생기지 않으며 위의 처리 로직이 필요하다.
- 반납·취소·상태 변경도 같은 잠금 순서를 따르고, 이미 처리된 요청의 재실행이 이력을 훼손하지 않는지 테스트한다.

## 5. 확인 방법

- 테스트 DB에서 두 세션을 동시에 시작시키는 도구(스크립트, 부하 도구)로 경합을 만든다. 순차로 두 번 호출하는 것은 동시성 테스트가 아니다.
- 결과뿐 아니라 최종 데이터(건수, 중복 점유, 이력)와 로그를 확인한다. 교착·직렬화 실패가 나면 재시도 정책과 사용자 메시지를 정한다.
- 실행 환경을 쓰지 못하면 "동시성 미검증"으로 보고한다.

## 6. 체크리스트

- [ ] 변경 서비스에 `TransactionScope: true`, 필요한 격리 수준을 정확한 이름으로 지정했다
- [ ] 업무 오류 반환 뒤 변경 SQL이 실행되지 않는다(또는 의도적으로 예외로 롤백한다)
- [ ] 잠금 순서가 모든 쓰기 경로에서 같다
- [ ] 불변 조건은 DB 제약으로도 막혀 있다
- [ ] 재시도해도 중복 저장되지 않는 업무 키가 있다
- [ ] 동시 요청·재시도·권한 없는 계정 테스트 결과를 수행 수준과 함께 보고했다
