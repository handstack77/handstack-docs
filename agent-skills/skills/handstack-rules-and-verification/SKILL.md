# 업무 규칙에서 검증까지

기능이 어려워지는 지점은 코드가 아니라 **규칙의 해석**이다. 같은 규칙을 화면, SQL, 함수에 각자 다르게 구현하면 결과가 갈리고, 경계(한도 5건, 기한 당일)와 동시성은 정상 경로 테스트로는 드러나지 않는다. 이 스킬은 규칙을 먼저 고정하고, 어디서 강제할지 정하고, 그 규칙에서 테스트를 뽑는 순서를 안내한다. 화면·계약 작성 자체는 `handstack-feature-delivery`와 각 계약 스킬이 한다.

## 1. 규칙 고정 (구현 전)

1. 요청에서 규칙 문장을 뽑아 **한 줄에 판단 하나**로 쪼갠다. "적절히 제한한다"는 쓸 수 없다. "저장 직전 해당 회원의 미완료 건수가 5 이상이면 새 건을 허용하지 않는다"처럼 **주체·조건·행동·적용 범위**가 보여야 구현과 검증이 된다.
2. 아래 표로 기록한다(작업 메모 또는 사용자에게 확인). 근거가 불명확하면 추측하지 말고 묻는다.

| 규칙 ID | 문장 | 적용 대상 | 근거/승인자 | 강제 위치 | 오류 메시지·코드 | 테스트 |
|---|---|---|---|---|---|---|

3. **용어·경계·시간**을 확정한다. "이상/초과", "당일 포함 여부", 기준 시각(서버 시간/사용자 시간대), 소급 적용 여부(규칙 변경 시 기존 데이터 처리)를 묻는다. 규칙 문장과 요구사항(시스템이 하는 일), 설계(버튼 위치)를 섞지 않는다.
4. 규칙 ID는 구현물에서 검색 가능하게 남긴다: `.dbc`/함수 주석, 출력 `ValidateRules`의 메시지, 테스트 이름. 프로젝트 주석 정책이 있으면 그에 따른다.

## 2. 강제 위치 결정

같은 규칙을 여러 층에 **각자 구현하지 않는다**. 정본은 서버 한 곳이고, 화면 검증은 사용자 편의다.

| 위치 | 적합한 규칙 | 한계 |
|---|---|---|
| 화면(`beforeTransaction`, 그리드 `validators`) | 필수 입력, 형식, 즉시 피드백 | 우회 가능. 서버를 대신하지 못한다 |
| `.txn` 출력 `ValidateRules` | 결과 데이터에 대한 후검증, 단순 조건 | 이미 실행된 뒤라 DB 변경을 막지 못한다 |
| `.dbc` (`<if>`, 사전 조회, `TRY/CATCH`) | 데이터 상태에 의존하는 규칙(중복, 한도, 상태) | 한 SQL 안에 많은 규칙을 넣으면 읽기 어렵다 |
| 함수(`.fnc`) | 복잡한 계산, 외부 호출을 포함한 규칙 | 전체 DB 롤백이 자동 보장되지 않는다 |
| DB 제약(유일/외래키/CHECK) | 동시성에서도 깨지면 안 되는 불변 조건 | 행 단위 제약만 가능 — 집계 한도는 쓰기 경로 설계가 필요 |

**저장 직전 서버 재검증**: 화면이 "가능"으로 보여 준 것은 확인 시점의 정보다. 저장 서비스는 규칙을 다시 검사한다(조회 서비스의 결과를 믿고 저장하지 않는다).

## 3. 조건이 여러 개면 결정표

조건이 셋 이상이거나 사유 우선순위가 있으면 `if` 중첩 대신 표를 먼저 쓴다. [결정표와 테스트 도출](references/decision-tables.md)에 작성·검증·테스트 변환 방법과 예가 있다. 핵심 규칙:

- 조건은 불리언으로 정의하고 "알 수 없음/조회 실패"는 불리언에 넣지 않고 별도 오류로 처리한다(정책 거절로 오인 방지).
- 여러 규칙을 동시에 어긴 경우 **대표 사유의 우선순위**를 정한다(모두 반환할지, 첫 사유만 반환할지는 정책 결정).
- 완전성(모든 조합이 어떤 규칙에든 해당)과 배타성(한 입력이 두 규칙에 해당하지 않음)을 둘 다 확인한다. 합계만 맞다고 끝내지 않는다.

## 4. 동시성·원자성·재시도

데이터를 바꾸는 서비스는 "두 요청이 동시에 오면?"과 "응답이 유실돼 사용자가 다시 누르면?"에 답해야 한다. 상세와 HandStack에서 확인된 동작은 [동시성과 재시도](references/concurrency.md)에 있다. 요약:

- 집계 한도·중복 방지는 **검사와 쓰기를 같은 트랜잭션**에 두고, 불변 조건은 DB 유일 제약으로도 막는다. 여러 행을 잠그면 **항상 같은 순서**로 잠근다.
- 소스상 dbclient는 **예외가 났을 때만 롤백**한다. SQL이 오류를 `Exception` 결과로 돌려주는 관례(`TRY/CATCH`)는 롤백을 일으키지 않는다.
- 재시도 안전은 업무 키(요청 키, 유일 제약)로 설계한다. 프레임워크의 `GlobalID` 검증은 재전송 방지 장치이지 업무 멱등성이 아니다.

## 5. 테스트 도출과 수행

[테스트 설계](references/test-design.md)를 따른다. 규칙마다 최소로 만든다.

1. 결정표의 열마다 1건 + **경계값**(한도-1, 한도, 한도+1 / 기한 당일 마지막 순간과 다음 날 첫 순간) + 대상 없음·잘못된 입력 + 권한 없는 계정.
2. 동시성 시나리오(같은 대상에 두 사용자, 같은 사용자의 두 대상)와 응답 유실 후 재시도.
3. 수행 수준을 구분해 보고한다: 정적(계약 점검) / SQL 단독(테스트 DB) / 거래 실행(`/transact/api/transaction/execute`) / 화면 시나리오. 실행하지 못한 항목은 "미수행"과 이유로 적는다. 운영 DB에서 쓰기 테스트를 하지 않는다.
4. 결함은 버전·환경·사전 상태·재현 절차·기대/실제 결과·로그(GlobalID)로 기록하고, 수정 뒤 재현 사례와 인접 기능을 다시 확인한다. 심각도(영향)와 우선순위(처리 순서)를 구분한다.

## 6. 완료 보고에 포함

규칙 표(강제 위치 포함), 결정표, 테스트 표와 수행 수준, 확인하지 못한 동시성·권한 시나리오, 사용자 결정이 필요한 규칙 해석(가정과 확인 요청).
